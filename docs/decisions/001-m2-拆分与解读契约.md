# 001 · M2 拆分与解读契约

- 日期：2026-10-09
- 状态：已采纳（自动执行的 M2 任务中按评审推荐默认值决定，用户可推翻）
- 输入：`docs/plan-review-2026-10-09.md` R01–R07 与第 5 节"四个决定"

## 背景

PLAN v0.2 的 M2 把改写、动画、流式 AI、离线、安全全部放在一个里程碑，而保存放在 M3，导致核心流程的"自动保存"在 M2 无法验收；AI 失败、拒答、取消的状态也没有定义。

## 决定

1. **M2 = M2a 本地闭环 + M2b AI 增强。** 两者共用同一套流程与结果页面，AI 只是另一个结果来源。
2. **首版使用方式：** 个人单实例，电脑启动，手机可访问同一实例。多人共享另作决策。
3. **默认输出：** 一种语气、两个简短读法候选、一个可编辑的小行动、一个开放反问；逐牌解读折叠展开。"换个视角"留在 M3。
4. **持久化起点：** M2 就保存本次完成记录（IndexedDB / Dexie）；记录保存结果快照，不随以后的 prompt / 牌义更新重算。历史列表、标签、导入导出留在 M3。
5. **离线承诺：** M2 的"本地模式"指不调用模型 API；PWA 断网重开是 M3 的独立验收项。
6. **安全分流：** 本地规则（关键词 + 排除语境）在客户端和服务端都执行，无 key 也生效；AI 路径在改写与解读的结构化输出里附带 `crisis` 标记，作为第二层，不额外增加请求。命中即中止占卜、展示求助资源。本地规则有识别局限，"100% 拦截"只针对固定测试集。
7. **流式边界：** 服务端接收模型 token，只把已完整解析、通过 Zod 校验的顶层章节作为事件推给前端；最终结果必须整体校验（含牌 ID / 位置 / 正逆位一致）才能保存。前端不会看到 JSON 碎片。
8. **验收数字：** "≤120 秒"与"90%"改为：本地路径 E2E + 固定评测集的硬检查（结构、牌面一致、禁词、行动非空、反问以问号结尾）100% 通过；真实模型评测需要 key，独立运行（`pnpm eval:live`）并记录结果；用户计时观察放到 M3。

## 后果

- 无 key 也能完整体验并留下记录，AI 失败时有明确退路。
- 真实模型质量在没有 key 的环境中无法验证，M2b 的"真实集成成功"需要用户本机配置 key 后跑 `pnpm eval:live` 补验。
