## 1. 结论

**M2 的核心功能已实现，但还不能按“验收完成”直接进入整包 M3。先收尾，再做历史与复盘。**

产品经理的判断：现在用户已经能完成一次对话，但“解释权留给用户”“本地不发送”“记录能找回来”三项承诺仍有具体缺口。首先修正这些承诺，随后让用户回看“当时怎么想、选择了什么、后来做了什么”。每日一张、换视角、海报有价值，但优先级低于可靠保存与回看。

技术主管的判断：保留 Next.js、领域模块、固定抽牌、统一结果契约、IndexedDB 与 provider 接口。无需换框架、引入服务端数据库或复杂 agent 编排。主要缺口在边界校验、异步生命周期及集成测试，现有业务 mock 没有覆盖这些交界处。

状态修正为：**M2a 功能实现、本地正常路径通过；M2b 功能实现、业务 mock 通过；M2 收尾与真实 AI 验收待完成。** 真实模型条件暂不具备时，可以在本地收尾通过后推进 M3a，不能把该条件隐去并宣布 AI 完成。

## 3. 需要先处理的发现

下列 **P1** 是 M2 收尾项，**P2** 是扩展功能 / 完整作品交付前的修订。本报告的待办均未实施。

### R01 · P1 · 全程本地的选择发生得太晚

**事实：** `ReadingFlow.tsx:190–193` 在有 key 时自动进入 rewrite；`:114–125` 立即调用改写接口。起问页 `:325` 写“问题只保存在你的浏览器里”，但本地 / AI 按钮与发送说明到 `:500–515` 才出现。用户后来选择本地，问题已经可能发给模型。

**意见：** 在首次提交前明确模式与发送说明；本地模式跳过一切模型操作，包括改写。AI 后切本地，只能承诺之后不再发送，不能抹去之前的发送事实。不要把是否配置 key 当成对单次输入的模式选择。

**验收：** 配置 key + 全程本地时，`/api/rewrite` 和 `/api/reading` 均为零请求；AI 模式首次发送前可看到对应说明；失败与切换不会重抽。

### R02 · P1 · 危机规则的语境豁免会漏掉本人表达

**事实：** `src/features/safety/crisis.ts:33–48` 在同一分句命中电影 / 新闻等词时，靠一个较窄的第一人称规则决定是否豁免。探针中“我不想活了”为 true，而“看完这部电影，我不想活了”和“新闻让我更绝望，我活不下去了”均为 false。现有固定集缺少这种混合语境。

**意见：** 本人的明确危机表述先于虚构语境豁免；覆盖引用、第三人称、同句转折和不同标点，不能仅通过扩大禁词解决。

**验收：** 扩展固定危机集零漏拦，对照集零误拦；客户端、两个 API 入口一致。此标准只适用于固定集，不承诺现实输入零遗漏。

### R03 · P1 · 受控流式尚未受危机判定控制

**事实：** `src/features/reading/ai.ts:137–148` 遇到合格章节立即发送，没有等待 `crisis:false`。把 `crisis:true` 放到 JSON 最后，实际先输出五个普通章节，再发危机事件。`:158–164` 对缺失或字符串类型的 crisis 仍接受最终结果；`runRewrite` 的 `:209–218` 也可接受缺失标记。当前 `ai.test.ts:97–100` 只测标记在第一位。

**意见：** 输出信封必须严格校验布尔 crisis；判定未知时缓冲章节，只有明确 false 后才能释放，不能依赖字段顺序或 prompt 要求。true 立即停止、清空预览且不写普通历史。缺失、错误类型、矛盾重复或截断属于无效输出。

**验收：** 用字段换序等合成响应覆盖 provider 业务层和浏览器可见内容；危机用例不得先显示普通解读，不产生完成记录。这里只证实本地协议处理的缺口，未声称观察到真实模型发生同样输出。

### R04 · P1 · 请求隔离和超时还缺端到端保证

**事实一：** `ReadingFlow.tsx:162` 的异步 crisis 事件不带 requestId，`flow.ts:163–165` 无条件清掉流程。直接 reducer 探针确认，旧请求的 crisis 会清除正在生成的新请求。组件卸载清理 `ReadingFlow.tsx:79–81` 未 abort 解读；已中止 signal 进入 `runAiReading` 时也未在启动前检查。

**事实二：** `src/lib/ai/anthropic.ts:25` 的 SDK timeout 不能充当整个流的时限。使用实际安装 SDK + 内存假 fetch，timeout=5ms、返回 headers 与首个 SSE 事件后挂起，40ms 后仍在等待，手动 abort 才结束。安装的 SDK `client.ts:1537–1544` 在 fetch 返回后清除该计时器；项目流循环没有另外的整体 / 无进展期限。现有 timeout mock 只是直接抛错，无法发现它。

**意见：** 所有异步事件都校验会话 / 请求身份；取消、重开、卸载中止上游；已取消请求不启动 provider。业务层显式计时，超时保留问题、牌、自解，允许重试或本地继续。

**验收：** 实际 SDK adapter + 假 SSE 验证建立流后挂起；浏览器验证取消后立即重试、离开再返回、迟到危机 / 结果、双击调用次数。不能只断言 reducer 拒绝重复动作，就推断没有重复网络请求。

### R05 · P1 · 草稿恢复和保存失败需要可用退路

**事实：** `storage.ts:39–42` 直接 JSON.parse 后强转；`ReadingFlow.tsx:68` 只检查 stage 字符串；`flow.ts:195–201` 直接读取 generation.status。探针 `restoreFlow({stage:"question"})` 会抛 TypeError，异常快照仍在，下次刷新再次失败。`storage.ts:48–53` 静默忽略草稿写失败；`ResultView.tsx:170–178` 只报未保存，仍可马上再问，没有重试入口。

**意见：** 草稿单独版本化并校验；坏快照允许回到可操作界面，保留已有有效记录。草稿和完成记录分别反馈保存能力；结果保存失败保留当前内容并支持同 ID 重试。恢复承诺明确为“已提交步骤”，未提交 textarea 内容不能被现有测试误认为已覆盖。

**验收：** 合法 JSON 但缺字段 / 错版本 / 错牌阵、localStorage 与 IndexedDB 分别不可用、保存失败后重试、恢复旧完成记录；均不崩溃、不静默丢失、不重复创建。涉及实际 schema 变更或迁移时，先提交兼容方案并按项目红线确认。

### R06 · P1 · 自动保存了用户没有作出的行动承诺

**事实：** `flow.ts:147` 生成时将行动设为 accepted；`ResultView.tsx:134–138` 直接显示“就做这个 ✓”。本轮手机视口复现，未点击行动按钮也已勾选并保存。

**意见：** 建议与决定分开。默认未决定，明确操作才变为接受 / 编辑 / 跳过；以后行动是否完成又是独立反馈。保留自动保存结果，不要求用户必须接受建议才能结束。

**验收：** 生成后直接离开、刷新恢复，记录仍是未决定；点击后才改变。旧版默认 accepted 没有证据说明用户点过，不得迁移成“明确接受”或“已完成”。

### R07 · P1 · 真实模型评测需要有真正的失败门槛

**事实：** `evals/reading.test.ts:45–50` 用本地模板构造合格的模拟回复，证明管道能接受它；`evals/live/reading.live.ts:36–42` 只以最终 result 统计 ≥90%。探针中含具体预测、两种相同读法和封闭式反问的输出仍返回 result，说明禁词 / schema 并不等同语义合格。

live 危机评测 `:45–50` 只有 console.log，无断言或逐例落盘，而且只覆盖改写。这里直接调用 `runRewrite`，**不经过 API 本地规则，不存在本地短路造成虚高的证据**。文件注释提到 README 人工分项评分，但 README 尚未提供。

**意见：** 分开报告模型完成率、被接受结果的硬约束、危机分流和人工语义质量。完成率 ≥90% 可作首轮可靠性目标，但安全失败不能被平均分掩盖。无 key 的 skip 只能写未验收。先小规模真实 provider 冒烟，确认协议与可用性，再跑完整集。

**验收：** `PLAN.md` v0.4 已加入版本、运行数、逐例结果、延迟、分项语义和独立安全门槛；补 API / 客户端 / UI 的 AI mock 流程，完成改写与解读两条 live 安全集。人工审核是否回应问题、不替用户判断他人动机、读法不同、行动可做、反问开放。

## 4. 产品扩展前的修正

### R08 · P2 · 先定义可靠回看，再增加玩法

M3a 建立历史与行动复盘：原问题、当时的读法、用户作出的选择、后来感受分别展示；始终显示保存时快照，不能因换 prompt 或牌义重算过去。

M3b 的换视角是附加快照，保留同一组牌和原选择；每日一张先定义当地日期、时区、重复进入与跨午夜规则，使用独立一张牌模板；正逆位设置只影响下次抽牌。不要把“展开详情”“换语气”“长文深度解读”混成同一个未定义功能。

3–5 人观察应在收尾稳定后开始，及时影响 M3；关注理解非预测、知道可以拒绝、能说出自己的下一步及找回记录。分开记录系统等待与思考时间。两分钟先保留为目标。

### R09 · P2 · 私密备份和分享必须分成两个交付

当前 `CLAUDE.md` 的“导出 / 分享默认不含原文”与原 PLAN 的“导出导入不丢信息”需要消歧。完整备份经明确选择可含私密原文，用于无损恢复；分享默认只用通用牌面与关键词，按白名单重建并预览。

`local.ts:69` 会把自解直接放入整体结果，所以仅删除 request.question 无法保证分享不含原文。验收用合成姓名、事件、自解、行动编辑及笔记覆盖所有回显字段。

导入不能只跑 `readingRecordSchema`：还需牌阵合法、结果与原抽牌一致、用户选择一致、版本及大小预检；同 ID 冲突先预览，默认保留现有，事务写入防半条记录。未知未来版本拒绝并说明原因。

### R10 · P2 · 语义质量与交付维护继续保留

本地模板不理解自由问题的语义，关系类行动存在默认联系、感谢或共同活动的建议（`content/local-reading.json:13–37`）。在断联或需要边界的情境下未必适用；增加可独立完成的默认行动与人工对照样例，不能把“非空且 24 小时可做”当成合适。

上一轮 R10 抓图问题仍存在：`scripts/fetch-rws-deck.mjs:85–93` 遇失败继续，`:106–122` 仍覆盖来源清单，`:125–127` 才报失败。排入 M3c，采用暂存、全量校验、成功后更新；本次没有执行重抓或改动资源。

求助资源已有复核日期字段，但日期本身不是核验凭据；交付时补官方来源、适用地区、复核记录。PWA / Docker / 实际手机访问分别验收，不能用桌面模拟视口替代。无 key、不调用模型、断网重开是三个不同能力。

## 6. 二轮补充发现（v0.5）

同日第二轮文档—源码对照，基线仍为 `df42480`，未修改业务代码、测试与配置。下列为 R01–R10 之外的补充，已写入 `PLAN.md` v0.5；编号续接，不改变既定顺序。

### R11 · P1 · 本机 AI 接口可被跨站请求和局域网匿名调用

**事实：** `src/lib/http/json-body.ts:5–14` 不校验 content-type，两个 API 路由也不校验 Origin / Host。恶意网页可向 `localhost:<端口>/api/reading` 发 `text/plain` 跨域“简单请求”（不触发 CORS 预检）；响应读不到，但请求仍会用宿主的 key 调一次模型。README:54 另指导 `pnpm start --hostname 0.0.0.0`，同 Wi-Fi 设备可直连无鉴权接口。

**意见：** 接口强制 `application/json` 并校验 Origin / Host；服务默认绑回环，局域网开放做成显式授权（开关或随机访问 token）。

**验收：** 跨域 text/plain 探针被拒且上游零调用；未授权局域网地址不可用；README 写明同网段额度与内容风险。落 C1 与行为约定 5。

### R12 · P1 · 危机误判后没有返回编辑的退路

**事实：** `flow.ts:163–165` 的 crisis 动作重置全部状态，`CrisisSupport.tsx:43` 只有“返回首页”，其 onExit 还会 `clearSession`。关键词规则对引用、虚构讨论存在误判，误判一次用户输入的问题和自解全部丢失。

**意见：** 不提供“无视警告继续占卜”，但提供“返回修改我写的内容”，保留原文，编辑后重新走检查。

**验收：** 误判样例可返回且问题 / 自解不丢；修改后仍命中则再次分流。落 C2。

### R13 · P1 · 流式门控需配套 crisis 首字段约定

**事实：** R03 的修复要求缓冲到 `crisis:false` 才放行章节；若模型把 crisis 放在最后，首章节延迟约等于总时长，受控流式失去意义。

**意见：** prompt 规定 crisis 为第一个字段（服务端缓冲仍是硬保证，prompt 只用于降低正常路径延迟）；评测断言字段顺序并记录首章节延迟。落 C2 / C5。

### R14 · P1 · effort low 硬编码需要真实验证

**事实：** `src/lib/ai/anthropic.ts:36–39` 对所有 fast 任务（含解读）固定 `effort: "low"`；读法雷同、行动模板化时没有校准依据。

**意见：** 首轮真实冒烟对比 low 与默认 effort 的成功率、延迟和语义分，写明解读升级 deep 的触发条件。落 C5。

### R15 · P2 · 记录契约缺牌组与设置快照

**事实：** `contract.ts` 的 Request / Record 没有 `deckId`；`CardImage.tsx:15` 与抽牌桌永远渲染全局默认牌组。M3b 牌组切换后，旧历史会静默改用新牌组呈现，违反“历史是保存时快照”的原则。

**意见：** schema v2 增加 `deckId` 与正逆位开关快照；兼容方案先写、按项目红线确认；v1 旧记录不伪造字段，按缺省牌组渲染且可识别。落 C4 / M3a。
