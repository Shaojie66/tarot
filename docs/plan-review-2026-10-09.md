# 《此刻三张牌》产品与技术评审

> 日期：2026-10-09（Europe/London）
> 重点：`docs/PLAN.md` v0.2；对照项目规则、README、当前源码、牌义内容与测试。
> 代码快照：`77f95b6`，M0 / M1 已标记完成。审阅期间 M1 从工作区改动提交为正式版本，本报告按更新后的状态撰写。
> 性质：建议稿，供下一版计划取舍；本报告不替代已确认决策。

## 1. 判断与推荐顺序

**继续使用现有技术栈，把下一步重点放在“完成一次可信的自我对话”，先于增加展示功能。** 当前 Next.js、内容数据、抽牌纯函数、provider 抽象足以支撑这个规模，无需增加后端服务、数据库服务或复杂的 agent 编排。

计划明确了开源、自托管、非预测工具的方向，但还没有把三个关键问题写到可以直接实现的程度：怎样保证牌义不替人下结论；AI 失败时这次体验如何继续；用户最终如何留下自己选定的一小步。

建议按下面顺序推进：

1. **先修内容规则与高风险牌义。** 现有内容已经有与产品定位相冲突的语义断言；禁词测试通过无法证明内容合格。
2. **把 M2 拆成 M2a 本地闭环、M2b AI 增强。** M2a 就包含抽牌、自解、本地解读、小行动及最小保存；M2b 再接 AI、失败恢复和流式显示。
3. **先定解读数据和状态，再做动画。** AI、静态模板、历史、导出共用结果结构；重试不会重抽，取消不会被迟到响应覆盖。
4. **把数字验收变成可复现的检查。** “两分钟”“90%”“100% 拦截”需要测试条件、样例与独立的通过规则。

这些建议保留“完整作品”的目标，调整的是依赖和交付顺序。账号、云同步、付费、埋点和线上运营没有必要重新加入。

## 3. 按优先级的建议

这里的 **P1** 指进入 M2 实现前或 M2 内必须解决的内容；**P2** 指应在 M3 / 完整作品交付前解决的内容。计划缺口不等于现有运行故障。

### R01 · P1 · 将“解释权留给用户”落实到牌义，而不只写在首页

**已证实的内容问题。** `PLAN.md:14` 将解释权交给用户，但 `content/cards/major.json` 中有：

| 位置 | 当前表述 | 问题 |
|---|---|---|
| 第 70 行，死神逆位 / 关系 | “关系已经名存实亡，却没人说出口。” | 直接替用户确认关系状态 |
| 第 60 行，正义逆位 / 关系 | “双方的付出明显不对等。” | 在没有事实的情况下判断关系失衡 |
| 第 85 行，高塔逆位 / 含义 | “你感到危机将至却在回避……” | 预设危机与用户的心理原因 |

这些内容会由百科页直接显示（`src/app/cards/[id]/page.tsx:99–108`），计划还会将同一内容注入 AI 解读。当前 `BANNED_PHRASES` 只检查六类词（`src/features/cards/schema.ts:39–40`），上述句子不命中也能通过。

**建议：**内容标准增加“不能仅凭牌面确认用户处境、他人动机、关系结论或未来事件”；对 78 张牌的正逆位、各主题和反问做一次语义审稿。不要只是给断言加“可能”二字。

例如，死神逆位可改为：“这张牌可以邀请你观察：有没有一种相处方式，你想调整却一直没有谈起？如果这不符合你的经历，可以跳过这条读法。”

用户界面也应允许“这不符合我的情况”，并允许接受、编辑或跳过小行动。这样才能把解释权变成实际操作。

**验收：**优先审查死神、高塔、恶魔、宝剑等容易引起强烈联想的内容，再全量审稿；任何一张牌都不能直接推出“该分手 / 该辞职 / 对方有问题”。禁词检查保留为辅助检查。

### R02 · P1 · 先完成本地闭环，再叠加 AI；最小保存前移

**计划依赖没有对齐。** `PLAN.md:75` 的核心流程包含自动保存，但历史与持久化安排在 M3（第 122 行）；M2 又同时包含改写、动画、流式 AI、离线和安全判断，失败定位会变得困难。

**建议：**M2a 先交付“选问题 → 固定抽三张 → 可选自解 → 本地解读 → 选择或修改小行动 → 保存本次记录”。完整历史界面、标签、筛选和导入导出仍留在 M3。M2b 对同一流程加入 AI，不再另建一套结果页面。

本地模板不能只是把三段牌义拼起来，应明确按“此刻 / 阻碍 / 下一步”组织内容，并提供行动引导；可以先用规则模板，不必立即制作庞大的行动库。

**验收：**无 key 时用户能走完流程、知道下一步做什么、刷新后找回本次记录。用户拒绝 AI 建议或不填自解，也能正常结束。

### R03 · P1 · 定义 AI 与本地模式共用的数据契约和失败状态

**技术设计缺口。** `src/lib/ai/provider.ts:6–23` 已支持 schema 入参与取消信号，但事件只有 `text / done / refusal`。还缺少业务结果、终止原因、验证及恢复约定。

建议在 `reading` 领域明确以下契约；provider 继续保持通用，业务类型不必塞进供应商适配层：

| 契约 | 至少需要约定的内容 |
|---|---|
| `ReadingRequest` | 主题、原问题、用户确认后的问题、可选自解、`spreadId`、固定抽牌及正逆位设置 |
| `ReadingResult` | 整体解读、按 `cardId + position` 对应的逐牌解读、解释候选、小行动、反问、来源 `local / ai` |
| `ReadingRecord` | 稳定 ID、`schemaVersion`、时间、请求快照、最终结果、用户选择；记录适用的内容 / prompt / 模型版本 |
| 状态 | 收集输入、检查输入、牌已固定、生成中、结果完成、拒答、技术失败、用户取消；保存成功 / 失败单独反馈 |

`isValidDraw` 是已有可复用函数（`src/features/draw/draw.ts:30`），不是已经接通的服务端防线。建议将 `PLAN.md:94` 改成“抽牌及校验函数已完成，API 接入待 M2”。服务端应从受支持的 `spreadId` 决定牌数与位置含义，不能信任客户端自报的任意数量；最终结果还要核对牌 ID、位置和正逆位与原抽牌一致。

**建议的恢复规则：**鉴权失败给出配置提示；超时、断流或结果不合格时保留问题、自解和牌，允许重试或转本地；取消后忽略迟到结果；同一操作进行中避免重复触发。模型拒答和技术失败分别处理，不能都静默转成本地占卜。

**验收：**用模拟 provider 覆盖成功、错误 key、超时、断流、截断 JSON、重复点击、取消后返回、输出牌不匹配。重试与切换解读来源均不重抽、不重复保存。

### R04 · P1 · 写清流式结构化输出的展示边界

**技术设计缺口。** 计划同时要求流式解读、JSON schema 和安全护栏（`PLAN.md:55、62、95–96`），但没有说明未完成、未校验的 JSON 如何进入界面。收到 token 不等于已经得到可显示的合格解读。

**建议分两步做：**先接通“完整结果 → Zod 与业务校验 → 展示”，界面提供进度状态；随后在 M2b 内增加流式呈现。若要逐段展示，就定义有边界的章节事件和逐段检查规则，不能把原始 JSON token 直接当解读输出。只有完整校验成功的结果进入正式历史，未完成结果可另存为明确标记的草稿。

Anthropic 官方文档说明结构化输出支持 streaming，但拒答和达到 `max_tokens` 时仍可能得不到符合 schema 的完整结果；支持的 JSON Schema 是子集。因此还需要供应商 schema 适配和本地最终校验，不能只依赖“要求模型输出 JSON”。[官方 Structured outputs 文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)（2026-10-09 核对）

**验收：**中断输出不产生伪完整记录；无效结果不出现 JSON 碎片；用户取消后不继续更新页面；结构合法但牌不匹配的结果仍判失败。

### R05 · P1 · 将安全检查放进流程，明确无 key 时的边界

**计划缺口。** 项目已有危机分流红线，但成功流程（`PLAN.md:73–76`）没有标出检查节点，规则文件又将安全分类归入 AI 快速任务（`CLAUDE.md:24`）。仅依靠远程模型会让无 key 路径缺少同等明确的处理方案。

**建议：**原问题进入 AI 改写前做输入检查；用户编辑后的问题、自解内容进入解读前再次检查。无 key 模式也要有独立的本地分流规则和静态支持页面；承认本地规则的识别局限，不把关键词命中等同于完整判断。命中危机后的流程应终止占卜，不能因 AI 故障转入普通静态解读。

测试既包含明确危机样例，也包含“最近低落”“讨论死神牌”“引用故事内容”等非危机样例，分别统计漏拦截与误拦截。求助内容应标明适用地区、核对日期和维护方式；本报告不代填未经核实的号码。

**验收：**固定明确危机集在 AI 和本地两条路径均通过分流；无关词语不会直接导致误判。将“危机样例 100% 拦截”明确限定为固定测试集，不能表述成对现实输入的保证。安全失败不允许被总体质量分数抵消。

### R06 · P1 · 拆开“无模型可用”“断网可用”和“数据留在本地”

**已证实的表述缺口。** `PLAN.md:38、57` 把无 key 称为离线模式，PWA 却在 M3；第 134 行的“问题不出本机”与手机访问另一台主机上的 Docker 实例并不等价。

建议在计划和 README 中明确四种情况：

| 模式 | 推荐承诺 |
|---|---|
| 本机浏览器 + 本机服务，无 key | 服务运行且必要资源可用时，不调用模型 API 即可完成流程 |
| AI 模式 | 为对应操作发送必要的问题、自解和牌面上下文；说明可能发生改写、分类、解读、换视角等多次请求 |
| 手机访问电脑 / Docker | 页面与 API 经过运行应用的主机；历史属于手机当前浏览器的站点存储 |
| PWA 断网重开 | 作为单独能力验收，写明首次加载、缓存范围、更新和断网时不可用的功能 |

“单次 AI 请求”的表述应改成“每次明确操作发送所需内容”，不能让人理解成整轮体验最多只发一次。默认无 key 路径也应能在已有 key 的情况下由用户主动选择。

分享图默认仅输出通用牌面、关键词等内容会更清楚；只去掉问题原文仍可能由 AI 解读复述姓名或具体事件。包含个性化解读时先展示预览并让用户选择。普通历史导出则应说明它包含私密原文，避免与分享图混淆。

**验收：**用合成姓名与经历检查默认分享图；确认 key 不进入浏览器 bundle、历史或导出；错误日志不含问题、自解、结果或 SDK 请求正文。PWA 的公共资源缓存与个性化内容分开设计。

### R07 · P1 · 把“两分钟”和“90%”变成可以复验的验收

**验收设计缺口。** `PLAN.md:121` 没有说明计时起止、输入长度、设备、网络、样本量或通过标准。用户主动思考一分钟不能被当成系统性能失败，结构正确也不能代替解读有用。

建议先用以下方案启动验证，数值是评审建议，不是已实现承诺：

- 默认呈现一个语气、两个简短解释候选、一个可编辑的小行动和一个反问；逐牌长解释折叠展开。这样能同时满足“一种风格”和“至少两种读法”。
- 用 3–5 位首次使用者做人工观察，记录是否无需指导完成、是否理解“不预测未来”、是否能说出自己的下一步。无需增加埋点；这只是小范围发现问题，不能据此宣称普遍有效。
- 计时分“系统等待”和“用户输入 / 阅读 / 反思”，注明机型、网络、模型、默认路径与是否跳过动画。两分钟先作为体验目标，根据实测再决定对外措辞。
- 建议建立首批 40 个固定解读用例，四个主题各 10 个；样例覆盖正逆位、跳过自解、模糊输入和不同牌位。危机与误拦截用例另设集合。
- 分项评估结构及牌面一致性、是否回应问题、是否凭空下结论、行动是否具体可做、反问是否开放。结构与牌面一致性作为硬检查；质量评分写明分母、阈值和人工判分依据，安全单独设通过门槛。

建议在 `evals/` 保存输入、固定抽牌、预期行为、禁止行为及版本信息。常规 `pnpm check` 用 mock，不需要联网和 key；真实模型集成验收独立执行并记录结果。

### R08 · P2 · 明确自托管的使用者，以及手机从哪里进入

**产品交付缺口。** 面向迷茫年轻人的使用体验与面向开发者的 clone / pnpm 安装路径，是两类不同需求（`PLAN.md:16、122`；`CLAUDE.md:3`）。对作品而言可以接受，但需要说清“谁启动服务，谁使用”。

**建议默认：**首版支持个人在自己的电脑运行；README 分“无 key 体验”和“启用 AI”两条路线，另写手机访问同一实例的步骤。Docker 默认按个人实例设计；若以后要多人共用，重新评审 API key、访问控制和数据隔离，不能把个人模式自然视为多人服务。

历史应说明按浏览器与站点隔离，换浏览器、设备或端口不会自动同步；浏览器数据被清理也不是云端可恢复的备份。

M3 在导入前做版本、字段、牌 ID、大小和重复记录预检，预览后事务写入；不支持的版本拒绝并说明原因，不静默丢字段。保存失败或存储不可用时明确标记“未保存”，保留用户导出的机会。这里提出协议建议，不是要求现在执行数据库迁移。

**验收：**未参与开发的人按 README 完成安装与无 key 流程；手机另走一次；仅键盘可操作、触屏可抽牌、减弱动画设置可用；有效导出能完整导入，损坏文件不留下半条记录。

### R10 · P2 · 修复资源重抓失败时会覆盖来源清单的问题

**已证实的脚本控制流缺陷，未执行失败重抓。** `scripts/fetch-rws-deck.mjs:85–93` 对缺信息或 HTTP 下载失败会继续循环，但第 106–122 行仍用本次成功项覆盖正式 `SOURCES.md`；失败牌的旧图留在原处，之后才在第 125–127 行报告非零退出。

因此，已有完整牌组时重抓一部分失败，会出现“图片仍有 78 张，来源清单却只剩部分条目”。现有测试只检查图片文件存在（`src/features/cards/cards.test.ts:44–48`），不会发现这个问题。

**建议：**抓取与转换先进入临时区，检查图片可解码、78 个 ID 和来源条目完整，再更新正式资源；失败保留上一版完整资源与清单。来源记录增加原始 URL、抓取时间和内容校验值可提高可追溯性。

**验收：**用 mock 模拟一张牌下载失败，确认旧图及完整来源清单不变；全量成功时，图片 ID 集合和清单 ID 集合严格一致。

## 4. 推荐的里程碑改写

| 阶段 | 交付内容 | 通过条件 |
|---|---|---|
| M1 内容质量补验 | 保留已完成标记，追加语义审稿和文档状态校正 | R01 的断言问题已修；百科、README、计划描述一致 |
| M2a 本地体验 | 起问、固定抽牌、基础翻牌、可选自解、本地解读、行动选择、最小持久化、本地安全分流 | 无 key 完整走通；刷新可恢复；用户可否定读法；静态内容通过审稿 |
| M2b AI 增强 | provider 实现、可跳过的改写、结构化解读、失败恢复、受控流式展示、AI 路径安全评测 | 真实集成成功；断流 / 超时 / 拒答 / 取消可恢复；不重抽、不错误保存；评测分项通过 |
| M3a 回看与日常使用 | 历史、标签、用户复盘、导入导出、每日一张、视角切换、设置 | 记录往返不丢信息；每日一张的日期 / 时区 / 当日复用规则清楚；用户能记录行动结果 |
| M3b 完整作品交付 | 分享图、Docker、PWA（若继续保留）、移动体验、安装说明 | 新使用者按文档跑通；分享内容符合默认边界；断网行为与文档一致 |
| A 美术支线 / M4 | 保留现有规划 | 不作为主流程完成的前置依赖；先用样张验证，再决定批量工作 |

M3 的“留存”可改叫“回看与复盘”。对这个非运营作品，更有意义的观察是用户回看时是否能辨认“当时怎么想、尝试了什么、现在有什么变化”，而非追求连续打卡次数。

## 5. 下一次修改 PLAN 前，应写明的四个决定

以下给出推荐默认值，便于将建议转成可执行计划：

1. **首版使用方式：**个人单实例，电脑启动，提供手机访问说明；共享给多人使用另作范围决策。
2. **默认输出：**一种语气、两个简短解释候选、一个用户可编辑的小行动、一个开放反问；详情折叠，深度功能放到明确阶段。
3. **持久化起点：**M2a 就保存本次完成记录；历史管理留在 M3。记录展示保存的结果快照，不因以后更新 prompt 或牌义而自动重算。
4. **离线承诺：**M2 指“不调用模型 API 的本地模式”；PWA 断网重开是独立验收项。错误 key、超时等不能让无 key 路径的价值消失。

建议先把这四项与 R01–R07 写进下一版 PLAN，再开展 M2 的页面与接口实现。
