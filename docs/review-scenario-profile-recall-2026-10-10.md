> **后续复评**：本文保留当时的实现与修复记录；最新结论见 [v1.2 复评](review-v1-2-2026-10-10.md)。回读 / 建档备份现已实现，但容量、提交时并发复核与失败恢复仍有缺口；“回读已实现”不代表完成闭环已验收。“建档存本地”不代表意图不会被发送给用户主动选择的模型，当前说明须补正。本文末尾的备份建议已不再是待确认项。

## 结论

方向合理：把“逐步收集用户信息”改成“点一张卡就开始”，减少了深夜输入的负担，也避免把用户的原话发给模型（卡片问句是固定文本，AI 只在生成那一步由用户明确点才发送）。隐私红线没破：建档与回读都只存本地、不推送、不收姓名 / 生日 / 登录。**但交付时有四个实质问题，已修；三项 PRD 内容未实现，已在 PRD 标注。**

## PRD 里没实现的（已在 PRD 标注，未做）

- **微定向层**（点卡后 0–2 道可跳过的选择题，如“关于你还是别人”“理解还是建议”）。
- **自解默认收起**（现在仍默认展开）。
- **反思提示**（Golden Thread 式一句可跳过的提示）。

## 值得留意但没改的

- 情境卡路径固定 `mode: "local"`，AI 只在解读步骤由用户明确点“AI 解读”时才用，符合“发送前明确选择”的红线；但此时 AI 不做问题改写（卡片问句本来就是固定的）。
- 回读到期提示靠本地时间和 localStorage，换设备不跟随——所以备份是否带上它是个产品决定（见下）。
- 保存 effect 的依赖里带了 `profile.recallCadence`，改节奏会触发一次无害的重复保存（`saveFlowRecord` 只写 `choice`）。

## 回读与建档进备份：建议

| 数据 | 建议 | 理由 |
|---|---|---|
| **回读（recall）** | **进备份，作为可选字段 `recalls`** | 它是指向某条记录的待办性质数据，换设备恢复记录时一并恢复才完整。导入时只补“指向的记录存在（本机已有或本次导入）且本机该记录还没有回读”的条目；到期的会立即显示提示 |
| **建档（profile）** | **进备份，但“只填空，不覆盖”** | 它是私密偏好，丢了要重答两三屏；但它和“设置”性质相近，而我们约定“设置不随备份覆盖本机设置”。折中：备份里带 `profile`，导入时**只有本机还没建档（`onboarded=false`）才采用**，已建档的本机不动 |
| 设置（逆位 / 牌组） | 仍不进备份 | 沿用已有约定：设备相关，不被导入覆盖 |

两项都沿用 `daily` 的做法：`backupVersion` 仍为 1，字段可选，旧备份照常可导入；预检时字段格式不对 → 拒绝整个文件。

**已确认并实现（2026-10-10）**：`buildBackup` / `parseBackup` / `applyImport` 支持 `recalls`、`profile`；导入预览会说明“补上几条回看提醒 / 这台设备还没建档会采用 / 不会覆盖已有设置”；记录事务失败时回读与建档一并恢复。单测 + e2e（新设备采用偏好、已建档设备不被覆盖、旧备份照常导入）。
